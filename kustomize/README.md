# Kustomize example: multi-environment app layout

A `base` + `overlays/{dev,staging,prod}` kustomize layout for one app
deployed across multiple environments - reusable wherever a template in
this repo needs this kind of worked example, not tied to any one addon.
Currently used by `enable_kargo` (`templates/gitops`), which generates
the `Application`s that promote into this layout - see "Using this with
Kargo" below. Not generated by any template itself - this is the app's
own repo content, same as app manifests always have been in this project.

Uses the same demo app as `examples/app/aws/` (`hashicorp/http-echo` +
the `DB_PASSWORD` secret).

## Layout

```text
.
├── base/
│   ├── app.yaml         # Deployment + Service
│   └── db-secret.yaml   # DB_PASSWORD via ExternalSecret (or a hand-created Secret, see below)
└── overlays/
    ├── dev/kustomization.yaml
    ├── staging/kustomization.yaml
    └── prod/kustomization.yaml
```

## Using this with Kargo

Copy `base/` and `overlays/` into your app's own repo root (the one
`app_repo_url` points at) - `overlays/{dev,staging,prod}` is the exact
path `templates/gitops` assumes sits under your `app_repo_path`, both for
the `Warehouse`/`Stage`/`PromotionTask` it generates and for the three
per-environment `Application`s it generates in `argocd/applications/`,
pre-annotated so Kargo is authorized to promote into them:

```yaml
metadata:
  annotations:
    kargo.akuity.io/authorized-stage: <APP_NAME>:dev   # <project>:<stage>
```

Kargo itself never creates an `Application` - it only promotes into one
that already exists, found purely by that annotation. `templates/gitops`
generates it for you so this repo's `overlays/` layout is the only thing
you still need to build by hand.

Each `overlays/<env>/kustomization.yaml`'s `images[].newTag` is the field
Kargo's `kustomize-set-image` promotion step rewrites - that's the actual
mechanism of a promotion: a real commit changing this one field, opened as
a PR, not a live `kubectl set image`.

## The DB_PASSWORD secret, without External Secrets Operator

`base/db-secret.yaml` is an `ExternalSecret` - it needs
`enable_external_secrets` on in your infra repo. Without it, delete that
file from your copy and create the plain Secret it would have produced
by hand instead, in each environment's namespace:

```bash
for ns in dev staging prod; do
  kubectl create namespace "$ns" --dry-run=client -o yaml | kubectl apply -f -
  kubectl create secret generic demo-db-credentials \
    --namespace "$ns" \
    --from-literal=db-password='<your password>'
done
```

## Testing an actual promotion

`hashicorp/http-echo`'s own published tags stop at `1.0.0` - checked
directly against Docker Hub, no tag above it exists, so
`kargo_image_repo_url: hashicorp/http-echo` has nothing new to ever
promote *to*. This example's `Warehouse` still shows the correct
subscription syntax, but you can't watch a live "new tag detected"
promotion with this exact image. To actually exercise the pipeline:

- Point `kargo_image_repo_url` at your own app's image instead (a
  registry you control) and push a new tag - this is how you'd use Kargo
  for real, and it's what the reference implementation this pattern was
  verified against does.
- Or temporarily point it at a public image with an active release
  cadence, e.g. `public.ecr.aws/nginx/nginx` (Kargo's own quickstart uses
  this image for the same reason), just to confirm the mechanism works
  before switching back to your real app's image.
