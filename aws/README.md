# Sample app - aws

A minimal Deployment + Service + Ingress to verify an infra repo (from
`templates/infra`) end-to-end: ALB creation, ACM wildcard cert
auto-discovery, `external-dns`. Not generated by any template. Two ways to
use `app.yaml`:

- **Standalone**: `kubectl apply -f app.yaml` directly against the infra
  repo's cluster - no GitOps repo needed.
- **GitOps-managed**: drop it into `apps/<name>/` in a generated GitOps
  repo (from `templates/gitops`) and push. No separate `Application`
  needed - the root Application's directory source recurses over the
  whole repo and applies any plain manifest it finds, same as
  `apps/cluster-addons/storage-class.yaml`.

Either way, replace the two `<APP_HOSTNAME>` placeholders with any
subdomain of the infra repo's `dns_zone_name` (e.g. `app.example.com`) -
the wildcard cert covers all of them.

## Why the Ingress looks like this

```yaml
metadata:
  name: app
  namespace: default
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS": 443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
spec:
  ingressClassName: alb
  tls:
    - hosts:
        - <APP_HOSTNAME>   # any subdomain of dns_zone_name - the cert is a wildcard
  rules:
    - host: <APP_HOSTNAME> # same value again, for HTTP(S) routing
```

- **`ingressClassName: alb`** - tells Kubernetes the AWS Load Balancer
  Controller (installed by the infra repo's `terraform/platform`, module
  `ingress-controller`) should handle this Ingress, not some other
  controller.
- **`scheme: internet-facing`** - the ALB gets a public IP/DNS name.
  Without it the controller defaults to `internal`, which wouldn't be
  reachable from outside the VPC at all.
- **`target-type: ip`** - routes ALB traffic straight to pod IPs (via the
  VPC CNI), the standard mode for EKS. The alternative, `instance`,
  targets NodePorts and is the legacy default - don't use it here.
- **`listen-ports`/`ssl-redirect`** - without `listen-ports`, the controller
  only opens port 80, no matter what's in `spec.tls`; the cert-discovery
  field only picks *which* cert to use on 443, it doesn't cause 443 to
  exist. Skipping this looks fine (HTTP works, `ADDRESS` populates) until
  you try HTTPS and it silently times out.
- **`spec.tls[].hosts`** - the ALB controller auto-discovers the wildcard
  ACM cert the infra repo issued (`modules/dns` in `terraform/cluster`) by
  matching this host against it, and terminates TLS with that cert directly.
- **`spec.rules[].host`** - same value as `spec.tls[].hosts`. `external-dns`
  (in `terraform/platform`) watches this and creates the matching Route53
  record automatically.
- **`metadata.name`/`metadata.namespace`** - name these whatever fits your app.

## Testing steps

```bash
kubectl get ingress -n default app -w   # wait for ADDRESS to populate (the ALB)
kubectl describe ingress -n default app # confirm no errors from the ALB controller

# give external-dns a minute to notice the Ingress and create the record
curl -I https://<APP_HOSTNAME>
```

Expect `hello from the sample app`. If `ADDRESS` never populates, check the
controller's logs (`kubectl logs -n kube-system deployment/aws-load-balancer-controller`)
for `AccessDenied` or webhook errors before assuming the Ingress spec is
wrong. If the ALB is up but the hostname doesn't resolve yet, check
`kubectl logs -n kube-system deployment/external-dns` instead.
